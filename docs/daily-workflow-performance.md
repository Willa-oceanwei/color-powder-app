# 生產單、配方管理與出貨單的編輯效能

- 生產單建立：只複製三個搜尋欄位，以一次 records 轉換建立選單，避免逐列產生 Pandas Series；完整編號優先、多條件文字搜尋、附加及停用標記仍沿用原規則。
- 配方管理：預覽及色母兩處選單共用標籤快取，只雜湊五個顯示欄位；原地修改名稱、狀態、順序或換一份資料時會自動重建。快取不含資料庫查詢。
- 出貨單：同一貨品快照共用大小寫、C 前綴別名及品名索引。完整編號優先於別名與部分比對，多筆結果仍須選擇。重讀或開始另一份編輯而換了貨品快照時會重建索引；客戶及日期變更後的歷史名稱索引隨歷史快照更新。

這次只減少衍生資料的處理，沒有延長資料讀取的快取期限，也沒有改動儲存交易、版本檢查、定價、庫存或列印計算。

## 可重現的局部運算量測

在 repository 根目錄執行 `python scripts/benchmark_daily_workflows.py`。
腳本與基準 commit `a6bd81eb04d3bc1e8c07917c23f4f2e596a3ed10` 比較，
使用 5,000 筆模擬貨品／配方、46 欄配方資料；先暖機，再取九次的中位數。
出貨單測量 30 列、三輪完整編號比對，另列出建立索引的時間。

Python 3.11、Pandas 2.2.2 的本機樣本：

| 局部工作 | 修改前 | 修改後 |
| --- | ---: | ---: |
| 出貨單重複貨品比對（索引已建立） | 14.02 ms | 0.02 ms |
| 配方管理兩處標籤處理（快取已建立） | 22.52 ms | 4.42 ms |
| 生產單未篩選配方選單準備 | 121.81 ms | 79.28 ms |

這些數字不包含瀏覽器、網路、資料庫及其他畫面工作，不能當作整頁加速比例。
較小的資料集可能感受有限；部署後仍應使用既有 PERF 紀錄觀察實際耗時。

## 驗證

新增測試涵蓋 `27706M` 與 `27706M-1` 的完整編號優先、C 前綴、大小寫衝突、
歷史名稱、快取結果隔離、貨品快照更新、配方原地修改與重複編號第一筆的選取規則。
既有畫面測試驗證連續表格修改沿用同一索引，並涵蓋自動帶入、儲存、取消及生產單操作。

Windows 執行 Streamlit 1.45.1 的 AppTest 時，使用 Python UTF-8 模式。
若 AppTest 開啟 script_runner 的 DEBUG widget dump，既有的「效能紀錄不含單據內容」
測試會連框架的 widget 記錄一起檢查；該現象在基準 commit 亦可重現。
驗證時可加 `--log-disable=streamlit.runtime.scriptrunner.script_runner` 排除框架的 DEBUG dump，
保留 `color_powder.performance` 的紀錄與斷言。

上述設定下，三頁相關的 169 項測試通過；所有資料庫操作均使用測試 SQLite。
